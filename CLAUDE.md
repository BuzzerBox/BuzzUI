# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

BuzzUI is the web app for the BuzzerBox, a quiz-show buzzer system that runs on a Raspberry Pi 4 (Raspberry Pi OS Lite, 64-bit, Trixie; the image is built from `provisioning/`, an Ansible playbook, while `install/` is the old installer for Raspbian Buster). It has three TypeScript parts with **no build-level linking between them**: each `npm` project imports the others by relative path.

- `server/` – Node/Express + `ws` game server. It is the single source of truth for game state.
- `client/` – Angular 21 (NgModules, Angular Material, Karma/Jasmine) SPA used by both the game master and the display screen.
- `shared/` – enums, packet interfaces and helpers imported by both, through `shared/shared.ts` (the barrel). It has no build of its own.
- `config.json` (repo root) – runtime config that both the server and the client import directly as JSON.

## Documentation

For every feature or change you develop, check the documentation and update it in the same branch:
- **Technical docs:** `docs/` (architecture, configuration, development, game file format, box settings, operations), the READMEs and this file.
- **User guide for hosts:** `docs/user/`. It names the English UI texts, with the German ones in parentheses for the main buttons.

Screenshots are in `docs/user/images/`. If a change alters a screen they show, either take them again or say in the PR that they're out of date.

## Commands

The `config.dev.json` file is gitignored, but **both client and server import it**. Builds fail without it, so create it first: `cp config.dev.json.example config.dev.json`.

Client (run in `client/`):
- `npm start` – `ng serve` on http://localhost:4200
- `npm run build` – production build to `client/dist/client`. `npm run buildDev` gives a dev build.
- `npm test` – Karma/Jasmine in Chrome. Run a single spec with `npx ng test --include src/app/services/game.service.spec.ts`. Add `--watch=false` for a single run (`--browsers=ChromeHeadless` without a window). Several older "should create" specs fail on `main` (missing providers or standalone components), so compare failures against `main` rather than expecting a green run.
- `npm run lint` – angular-eslint. It reports about 200 existing errors (mostly `prefer-standalone`/`prefer-inject`); compare the count before and after a change.

Tests: TestBed in Angular 21 is zoneless by default, but the app runs with zone.js (`provideZoneChangeDetection()` in `main.ts`). A spec of a component that updates itself from timers or subscriptions needs `provideZoneChangeDetection()` in its providers, or it fails with `ExpressionChangedAfterItHasBeenCheckedError`.

Server (run in `server/`):
- `npm run transpile` – `tsc` to `server/dist/`. Because `shared/` and `config.json` are compiled in, the entry point lands at `dist/server/main.js`.
- `npm start` – run the transpiled server (production config)
- `config.json` and `config.dev.json` are compiled into `dist/`, so after changing either one, run `npm run transpile` again before restarting the server.
- `npm run startDev` – start a virtual serial port pair via `scripts/open_serial.sh` (requires `socat`), transpile, and run with `--dev=1`
- There are no server tests.

Hardware simulation in dev: `scripts/open_serial.sh` links `/tmp/ttyV0` (the server side, set in `config.dev.json`) to `/tmp/ttyV1`. Run `scripts/send_serial.sh` to write buzzer/release bytes to `/tmp/ttyV1` from an interactive menu. To simulate a UDP buzzer, send its JSON packets to port 5005 (e.g. with `nc -u localhost 5005`), repeating the heartbeat at least every `heartbeatTimeoutInMS`.

Release packaging: `scripts/create-update-bundle.sh <private-key.pem>` (or `--unsigned`, run from `scripts/`) builds both projects through `scripts/create-installation-files.sh` into `install/.assets/compilations/` and packs them into `updates/buzzerbox-update-<version>.tar`, signed with Ed25519 (`scripts/update-signing.js`) and checked against `install/.assets/update-public-key.pem`. See `docs/operations.md`. `install/install.sh` (run as root, configured by `install/setup.env`) only installs onto an old Buster box.

Releases: a PR "Release X.Y.Z" from `release/X.Y.Z` raises `version.json` and lists the changes since the last release; it is squash-merged. The merge commit then gets a signed, annotated tag `vX.Y.Z` (message "BuzzerBox X.Y.Z"; `tag.gpgSign` is on). The tag must match `version.json`. Pushing it starts `update-bundle.yml` (the signed USB update bundle, which needs the `update-signing` environment) and `pi-image.yml` (the BuzzerBox image). They create the GitHub release with generated notes and attach their files.

## Architecture

**Config layering.** `ConfigService` exists separately in `server/services/` and `client/src/app/services/`. Both return `config.json`, or `defaultsDeep(config.dev.json, config.json)` in dev mode. The server decides dev mode from the `--dev=1` argument; the client uses Angular's `isDevMode()`. The config defines the server address/ports (WebSocket 4201, media file server 4202), the buzzer list (`key` for a browser keypress, `byte` for serial input), and serial settings. The client reads the server host through `ConfigService.getServerAddress()`: an empty `server.address` (the production default) means the host the page was loaded from, so the Pi's IP or hostname can change without a rebuild; `config.dev.json` sets `localhost`. `docs/configuration.md` lists every key. A buzzer may set `color` (`#rrggbb`) for its team's color on the screens. `join` (`wifiName`, `masterAddress`) is what the waiting screen tells the person hosting; it's built into the client, so it doesn't follow a `WIFI_SSID` changed in `buzzerbox.txt`.

**Communication.** Everything goes over a single WebSocket that carries JSON packets: `{packetType: EPacketTypes, ...}` (`shared/enums/EPacketTypes.ts`, with a matching `I*Packet` interface in `shared/interfaces/`). Adding a message means adding an enum value and an interface in `shared/`, exporting it from the barrel files (`shared/enums.ts` / `shared/interfaces.ts`), handling it in the `onPacket` dispatch in `server/services/game.service.ts`, and handling it in the client `GameService`'s message switch. The server only accepts `REGISTER_*`, `KEYPRESS_ON_SCREEN` and `UPDATE_MEDIA_STATE` (screens report when their media ended) from any connection; every other packet must come from the master connection, so a new master-only packet goes below that check. Enum values are numeric, so **append new packet types at the end of the enum** so existing values keep their numbers.

**Server game automaton.** `server/services/game.service.ts` (a singleton, like every server service, accessed through `X.get()`) holds teams, questions and the current state, and moves through `EGameStates`: `WAITING_FOR_MASTER → WAITING_FOR_SETUP → WAITING_FOR_START → PLAYING → END`. It goes to `LOST_MASTER` if the master disconnects in the middle of a game; a reconnecting master then gets `NEW_MASTER_ACCEPTED` with the existing state. Only one master connection is allowed, but there can be many screens. The server pushes state to screens as `DATA_FOR_SCREEN` packets. Besides the question number and media state, `IGameState` holds the progress within the current question (marked teams, buzzer lock, logged in and revealed answers), kept up to date on both sides through `shared/helper/game-state.helper.ts`, so a reloaded screen or rejoining master shows it again. The server pings every connection every 10 s and drops those that don't answer, so a master whose device left the WiFi doesn't block it from registering again.

**Buzzer input.** Buzzers arrive in one of three ways:
- As bytes from a microcontroller on the serial port (`SerialPortService`). The server writes back to it through `MicroControllerSerialAdapter`, where each command frame is `[command, param-or-stuffingBit, eol]`. It also sends a heartbeat every `serial.heartbeatIntervalInMS`, so the box shows that the Pi is connected.
- As UDP packets from wireless ESP32 buzzers, handled by `UdpBuzzerService` (`udpBuzzer` in the config, port 5005). Their firmware is in the BuzzController repo (`wireless/`), whose README documents both protocols; change both sides together. A buzzer isn't configured: it announces itself with a heartbeat every second (`{t: 'HB', id: <MAC>, lp, seq, bat, fw}`) and presses send `{t: 'PRESS', id, n, ts}`. The server answers each heartbeat (`ack: seq`), each press (`pa: n`) and every change of lock, marked team or game state with `{t: 'STATE', selected, locked, game, st}`. `game` (`isGameRunning()`) keeps the battery-powered buzzers awake; `st` is the server's µs clock (`process.hrtime` since start), which the buzzers follow so that `ts` is on it. A press is resent until acknowledged, so the server takes each `n` once per buzzer. A buzzer's ID comes from its MAC (`udp:<MAC>`, `BuzzerHelper`); one that stops sending heartbeats is shown offline but stays in the list, so the list only grows and each buzzer keeps its `buzzerIndex` while the server runs. The server sends the master the whole list in `AVAILABLE_BUZZERS` whenever it changes, also when a buzzer's `batteryLow` flips (`batteryLowInMV`, with 100 mV hysteresis). Savegames find teams on UDP buzzers by ID and teams on the box's buzzers by index. Presses within `pressCollectionWindowInMS` are compared by `ts` (0 means the first to arrive wins), and the earliest one whose buzzer has a team wins.
- Wireless buzzers get the box's WiFi over USB when the master adopts them: `BuzzerProvisioningService` polls the serial ports for `udpBuzzer.provisioning.usbIds` (the Feather V2's CH9102, `1a86:55d4`, and the Feather ESP32-S3's own USB, `239a:8113`/`239a:811b`) and greets a new one to learn its MAC and firmware (a sleeping Feather V2 doesn't answer, so after 2 s a buzzer on one of `wakeUsbIds` is reset through RTS, which wakes it; an S3 can't be woken over USB, so it stays awake while plugged into a host, and resetting it would leave DTR low, which silences its USB serial; that reset is a `python3` ioctl helper, because serialport's `set()` sends TIOCCBRK first, which Linux's cdc_acm refuses for the CH9102, and then never sets the lines, so the port is opened with `lock: false` for the helper). The master gets the plugged-in buzzers and their state (`IUsbBuzzer`: identifying → detected/no-answer → adopting → adopted/failed) in `USB_BUZZERS` packets, shown on its home page in the list of connected wireless buzzers (`master/wireless-buzzers`, which merges them by MAC with the online UDP buzzers of `AVAILABLE_BUZZERS` and shows color, firmware, battery and USB/WLAN); "Übernehmen" sends `ADOPT_USB_BUZZER` (master only), and only then does the server send the WiFi name, passphrase and server address from `settingsFile` (`/etc/buzzerbox/wireless-buzzers.conf`, `KEY=value`, written by `buzzerbox-apply-settings` from `buzzerbox.txt`, readable by `dialout`). A buzzer's USB part goes away when it is unplugged. Buzzer firmware 1.1.0 and later appends the WiFi it has to `BUZZ READY` (`{"ssid","host","port"}`, never the passphrase); when it matches the box's settings, the list shows the buzzer as adopted already (`isAdopted`) with only "Erneut übernehmen". The list also sets the color of the buzzer's case (`BuzzerHelper.CASE_COLORS`, firmware 1.2.0 and later, `color` in `ADOPT_USB_BUZZER` and `BUZZ WIFI`); the buzzer keeps it in its flash and reports it in `BUZZ READY` and every heartbeat (`col`), so it becomes `IBuzzer.color`, and the server copies the buzzer's color onto `ITeam.color` (setup, team changes, and whenever a buzzer's color changes), which `TeamColorHelper` prefers over the index palette. A buzzer with a case color is named after it ("Blauer Wireless Buzzer", with the end of the MAC when two share a color), one without as "Funkbuzzer" plus the end of its MAC; the client names them in the master's language (`BuzzerNameHelper`, the server sends no name for a UDP buzzer), so a name follows the color. A new team on it starts with the color's name ("Blau", "Blau 2", `TeamHelper.makeDefaultName`) until it is renamed by hand. `isConnected` comes from `UdpBuzzerService.isOnline()` by MAC, and every UDP buzzer change resends `USB_BUZZERS` so the list follows it. Heartbeats also tell `fw` and, from firmware 1.3.0 on a Feather ESP32-S3 with its fuel gauge, `pct`, which become `IBuzzer.firmwareVersion`/`batteryPercent`. To try it in dev, point `udpBuzzer.provisioning.settingsFile` in `config.dev.json` at a file with your own WiFi and your computer's LAN address.
- As `KEYPRESS_ON_SCREEN` packets from a browser. This only works when `enableBrowserKeypressEvents` is true, which it is in the dev config only; both the screen (which then doesn't listen for keys) and the server check it.

The server maps either input to a team's buzzer, and handles the lock/soft-release state itself. A buzz marks the team and locks the buzzers; the master grades the answer in a dialog (`GRADE_ANSWER`). A correct or double answer adds the question's points (twice for double), reveals the correct answers and keeps the lock. A wrong answer subtracts the question's points (scores may go below zero), unmarks the team and releases the lock. Releasing from the master (`SET_BUZZER_LOCK` false, from the big button in the middle of the play page or "Ohne Wertung freigeben") also unmarks the team, like the soft release on the box.

**Client.** `app.routing.module.ts` lazy-loads two feature modules: `master/` (home → load-game or setup → prepare → play, protected by a `RouteGuard` that redirects based on the game state) and `screen/` (connect → main, the kiosk display that Chromium opens at `/screen/` on the Pi). `/choose` lets the user pick a role. Once the server sends the presetup data, the master lands on the `home` splash page instead of the setup. `services/game.service.ts` is the client's central state and packet handler for both the master and the screens (`useAsMaster()` / `useAsScreen()`); `game-screen.service.ts` is an unused empty stub. `web-socket.service.ts` wraps the rxjs `webSocket` and reconnects whenever the connection is lost, queueing messages sent meanwhile. Because the server forgets a client with its connection, `GameService.onReconnected()` rejoins: screens reload, a master still in setup registers again (keeping the form), and a master in a game reloads and rejoins it. There is no "start game" page: when the server confirms `SETUP_GAME`, or sends `NEW_MASTER_ACCEPTED` to a rejoining master, the client sends `START_GAME` right away (state `READY_TO_START` only lasts until the answer) and goes to the play page. During a game the master's toolbar shows the autosave icon and a ⋮ menu (Teams bearbeiten; Spiel beenden, which shows the end screen; Spiel pausieren and Spiel verwerfen, which go back to the home page without it: both send `RESET_SERVER`, which saves the state, and verwerfen sets `discardState`, so `AutosaveService.discard()` deletes the state instead; all three with a confirmation). "Server zurücksetzen" is only on the home page; every master page but the play page has a logout button, which reloads at `/choose` and so gives up being the master. After the last question, "Spiel beenden" replaces "Nächste Frage".

**Screen themes.** The look of the screens is chosen per game in `prepare-game` ("Aussehen der Anzeige") and travels as `IGameState.themeId` (also in `ISetupPacket.themeId`), so it is saved with the state and reaches screens and a rejoining master through the existing packets. Missing or unknown IDs mean the default. `client/src/app/themes/screen-themes.ts` is the registry (`studio` = dark, the default; `daylight` = light; `classic` = the look before themes; their names and descriptions are the texts `themes.<id>.name`/`.description`), and `ScreenThemeHelper` resolves a theme and sets `<html data-screen-theme="…">`. Each theme has a style:
- `classic`: the screen components' original `:host(.screen)` CSS, with no effects.
- `show`: rules under `:host(.screen.show)` (each screen component binds the `show` host class) with colors and fonts from `--bb-*` variables in `themes/themes.scss` (e.g. `--bb-glow`, currently 0). It adds team colors (`TeamColorHelper`, per buzzer index), the buzz banner, grade flashes and counting points, a crown, A–D answer badges, a progress bar, the branded waiting screen and the podium.

A new show theme only needs a registry entry and a variable block. The master stays light in every theme (it only shows the answer letters in show themes). Before a game, a screen uses its last game's theme from `localStorage`. Rubik and the Material Icons font (`material-icons` package) are bundled through `angular.json`, since the box has no internet; don't load fonts from Google. The build puts them in `fonts/` (`outputPath.media`), not Angular's default `media/`: behind a reverse proxy (the test host's Caddy), `/media*` goes to the file server, so fonts there would be missing.

**Languages.** (PR #147, branch `feature/i18n`, not merged into `main` yet.) The UI is in English (the default, until the master chooses a language) and German. All texts are in `client/src/i18n/<language>.json` (nested keys, `{{parameters}}`, and `.one`/`.other` pairs for texts with a number); `i18n.spec.ts` checks that both files have the same keys and parameters. They are bundled, not fetched, since the box has to show them right away. Templates use Transloco's pipe (`{{'common.cancel' | transloco}}`, with `TranslocoModule` in the module's or standalone component's imports); code uses `t()`/`tn()` of `app/i18n/i18n.ts`, which read the same files without injection, so helpers can use them too. Don't keep a translated text in a field: keep its key and translate it where it is shown, so it follows a change of the language. `LanguageService` holds the language and remembers it in `localStorage`; `LanguageHelper` in `shared/` lists the languages. The master chooses it (`app-language-switch` on `/choose` and in the master's toolbar, in the ⋮ menu on the play page) through `GameService.setLanguage()`, which sends `SET_LANGUAGE`, also whenever it registers; the server keeps it and passes it on to the screens (also to one that registers later), which follow it. Specs get the German texts through `test.ts` (`SPEC_LANGUAGE` in `i18n-testing.module.ts`), whatever the default is. The server's own messages (storage, update and box settings errors) are English only. A new language needs its file, an entry in `LanguageHelper.LANGUAGES`, `TRANSLATIONS`/`LANGUAGE_NAMES` in `i18n.ts` and a locale in `FormatHelper`.

**Box settings.** On `main`, `BoxSettingsService` reads `boxSettingsFile` once when the server starts. `buzzerbox-apply-settings` writes that file from `buzzerbox.txt` on every boot; without it, the defaults apply. Its only setting so far is `ANALOG_BUZZERS=no`, which makes the master offer only the wireless buzzers.

The rest of this paragraph describes PR #141 (branch `feature/box-settings`), which isn't merged yet. The gear icon on the master's home page (`showSettings` of the toolbar) links to the page `master/box-settings` (`/master/settings`, only while no game is set up; leaving it with unsaved changes asks first), which shows the box's settings from `buzzerbox.txt` on the boot partition (WiFi, addresses, hostnames and, from #129, the TV resolution and touch display; `BoxSettingsHelper` in `shared/` has the keys, defaults and validation). The master asks with `REQUEST_BOX_SETTINGS` and gets `BOX_SETTINGS`; `BoxSettingsService` reads the file (`boxSettings.file`) and `defaultsFile` for missing or invalid values. Only if the file has `EDIT_IN_MASTER=true` can the master change them (`SAVE_BOX_SETTINGS`) and restart the box (`RESTART_BOX`), both only while no game is set up; the server can't write the boot partition, so it runs the root helper `install/.assets/scripts/buzzerbox-settings.sh` through sudo (`boxSettings.writeCommand`/`restartCommand`), which checks the flag and values again. Its validation repeats `isValid` of `buzzerbox-apply-settings`, so change all three together. The update bundle's post-install hook and the Ansible `buzzerbox` role install the helper and its sudo rule. In dev, `useHelper: false` makes the server write `server/box-storage/buzzerbox.txt` itself (created with the defaults and editing allowed), and it can't restart.

**Games and storage.** A game is a folder (`games/<name>/` in `storage.boxPath` on the box, `buzzerbox-games/<name>/` on a USB stick, i.e. every folder in `storage.usbPath`, which defaults to `fileServer.localPath`). It holds immutable versions (`versions/<n>.json`, `IGameDefinition`), states (`states/<name>.json`, `IGameInstanceState`: teams and progress, pinned to one version) and `media/`, to which question media paths are relative. `server/services/storage.service.ts` implements it, and `StorageApiService` serves it as a REST API under `/storage` on the file server port (routes documented in `shared/helper/storage-api.helper.ts`). Every request needs the token the master gets in a `STORAGE_ACCESS` packet when it registers. `SETUP_GAME` carries an `IGameStorageRef`; `AutosaveService` then writes the state a second after each change (debounced, retried when a stick is pulled out) and reports in `AUTOSAVE_INFO` packets. The box has no reliable clock, so timestamps use `ClockService`, which takes the master's time from `REGISTER_MASTER`. A version can hold `mediaDefaults`: how media questions start (by media kind), unless a question has its own `initialConfig`. Client: the editor (`setup`, questions only) saves versions; `prepare-game` chooses the teams and the screen theme and sets up a new or continued state, which starts the game. It fills in the media defaults (`MediaHelper.applyMediaDefaults`) and resolves relative media to URLs with `StorageService.resolveMediaUrls`; `game-list`, `media-browser` and `game-import` (bundles and old v2/v3 savegames, converted in `GameFileHelper`) serve `load-game` and the `storage` manager. Navigation between them passes `IEditorNavigationState`/`IPrepareNavigationState` through `history.state`.

**Media.** `FileServerService` serves `fileServer.localPath` (USB sticks at `/media/pi` on the Pi) under `/media`, and the box's games under `/media/BuzzerBox`; only files with media extensions are served, so versions and states (which hold the answers) are not. A GET on `/media` returns a directory tree of the sticks; the editor uses the game's own media tree from the storage API instead. Only images (`.png .jpg .jpeg .gif .bmp .webp .avif`), video (`.mp4 .m4v .webm`) and audio (`.mp3 .wav .ogg .m4a`) are listed (`shared/services/file-extensions.service.ts`); video and audio are both "playable" media and handled alike. For local dev, `fileServer.localPath` points at `server/media/` (gitignored), where each folder stands for one USB stick (e.g. `server/media/DevStick/`), as on the Pi. Playback is synchronized to screens with `UPDATE_MEDIA_STATE` packets and uses `@videogular/ngx-videogular`.

**USB updates.** `UpdateService` looks for `buzzerbox-update-<version>.tar` in the `updates/` folder at the top of each stick (or in `update.bundleDirectory`). It checks each bundle's `manifest.sig` against `update.publicKeyFile` and sends the list to the master in `UPDATE_INFO`; the master shows it in `master/update-card` on its home page. `INSTALL_UPDATE` (master only, no game set up) runs `update.command` (`sudo -n buzzerbox-update start`). An unsigned bundle is installed only after the master confirms a warning, and the root helper checks the signature again, switches `current`, runs the post-install hook and rolls back if the new server doesn't start. The result is in `update.statusFile`.

In dev, `config.dev.json` can point `publicKeyFile` either at the production key, so the release bundles from GitHub show as signed, or at a dev key for bundles you sign yourself. Installing doesn't work in dev.

## Deployment notes

On the Pi, nginx serves the built client, and the Pi acts as a WiFi access point (hostapd/dnsmasq, default IP `10.0.0.5`, hostnames `buzzer.box` / `buzzerbox.local`). Chromium runs in kiosk mode on `http://localhost/screen/`. Per-box settings (WiFi, addresses, hostnames) are in `buzzerbox.txt` on the boot partition, see `docs/box-settings.md`; `install/setup.env` only applies to the old Buster installer.

**SSH and updating a box.** Log in as `admin` (`buzzerbox_admin_user` in `provisioning/group_vars/all.yml`), not `pi`: `ssh admin@10.0.0.5` after joining the box's WiFi. Only keys are accepted, and `admin` has passwordless sudo. `pi` runs the server and the kiosk, but it can't log in over SSH. The software is still installed under `/home/pi/BuzzerBox` (`current` → `releases/<version>`). To update over SSH, download `buzzerbox-update-<version>.tar` from the GitHub release, `scp` it to the box and run `sudo buzzerbox-update install <bundle>`, which restarts the server and rolls back if the new version doesn't start. `sudo buzzerbox-update status` shows the result. The box's clock lags (it has no RTC), so tar's "time stamp … in the future" warnings during the install are harmless.

**Test environment.** `.github/workflows/test-images.yml` builds `server/docker/Dockerfile` and `client/docker/Dockerfile` (build context: repo root) on every push to `main` and publishes them to GHCR as `ghcr.io/buzzerbox/buzzui-{server,client}:test`. The images use the production code paths, with `config.test.json` merged into `config.json` at build time (`scripts/merge-config.js`): browser keypress buzzers on, serial off (`serial.enabled`), media from `/srv/media`. `deploy/test/` holds the compose file and the cron-driven `update.sh` for the test host.
